## 一、技术选型报告

### 1.1 结论

**Node.js 单栈 · 零运行时依赖 · 直接操作 OOXML。**

### 1.2 候选方案对比

| 方案 | 优势 | 否决理由 |
|---|---|---|
| **Node.js 单栈（选定）** | 与 DSH 同进程零跨语言；可直接操作 OOXML 部件；复用宿主内置资源 | — |
| Python sidecar（python-docx/pptx/openpyxl/PyMuPDF） | 库生态成熟 | 本机 Python 3.14.7 且办公库一个未装，3.14 轮子可用性存疑；需跨进程协议、依赖分发、错误传播三套额外机制 |
| 现成 JS 库（SheetJS / exceljs） | 上手快 | **写回时会重建整个工作簿**，图表、宏、条件格式、透视表、外部链接会丢失，直接违反 §五.4 与 §十八.4 的保真要求 |
| 混合（Node + Python 重型件） | 能力上限最高 | 首期范围（XLSX）用不到；两套工具链的维护成本在阶段 3（PDF）再评估 |

### 1.3 为什么自己写 ZIP 与 XML

不是造轮子，而是**保真度要求决定必须自己写**：

1. **ZIP**：现成库的解压接口无法同时满足「复用未修改条目的原始压缩字节」与
   「按条目限制解压量、压缩比」。用 `node:zlib` 自己读写中央目录后，
   `toBuffer()` 对未修改条目直接透传原压缩流，这是「无关部件逐字节不变」的实现基础。
2. **XML**：任何「解析成对象树再序列化」的方案都会重排属性、规范化自闭合标签、
   改写命名空间前缀——对 OOXML 来说就是**每次保存都在污染整个文档**。
   自写扫描器只记录节点在源码中的偏移量，编辑产生「区间补丁」，
   序列化时按偏移拼接，未触碰的字节原样输出。

**代价**：约 900 行自研代码，需要自己保证正确性。
**回报**：零依赖（无供应链风险、无版本冲突、无安装步骤），且保真度可被测试直接断言。

## 二、技术方案

### 2.1 架构

```
DSH (ctx.tools)
      │
      ▼
lib/index.js            Cordis 插件：解析 defineTool → 注册 23 个工具
      │
      ├── capabilities.js   能力清单（版本/协议/能力枚举/NOT_IMPLEMENTED）
      ├── errors.js         错误码体系 + 统一响应信封（§4 / §13）
      ├── workspace.js      路径安全 / 真实类型检测 / 哈希 / 文件锁 / 事务
      ├── tools.js          工具定义层（参数校验、确认位、预览-执行-回滚）
      ├── xlsx.js           XLSX 适配器（stage 1 唯一格式适配器）
      └── ooxml.js          ZIP 容器 + 最小修改 XML 引擎（格式无关底座）
```

**分层原则**（§十八.2）：`ooxml.js` 不感知 XLSX 语义；`xlsx.js` 不感知工具协议；
`tools.js` 不含文件格式细节。阶段 3–5 新增 DOCX/PPTX/PDF 适配器时，
只需在 `tools.js` 增加工具声明，**不触碰** `ooxml.js` 与已有适配器。

### 2.2 最小修改模式（保真度的核心）

```
原始 sheet1.xml:  <row r="1"><c r="A1"><v>10</v></c><c r="B1"><v>20</v></c></row>
                                    └── 补丁区间 ──┘
输出 sheet1.xml:  <row r="1"><c r="A1"><v>99</v></c><c r="B1"><v>20</v></c></row>
                  其余字节（含 B1、行属性、命名空间、空白）逐字节原样
```

补丁区间重叠时**抛错而不是静默损坏**（`INTERNAL_ERROR`），
因为重叠意味着两个编辑意图冲突，静默取一个会产生错误文档。

> **踩坑记录（零长补丁不算重叠）**：重叠判定是 `start < prev.end && end > prev.start`，
> 因此**零长插入**（`patch(x, x, xml)`，`insertBefore`/`insertAfter` 就是这么实现的）
> 与「起点相同、终点更大的替换补丁」**不会**被判为冲突。
> 若先登记替换 `[x, y)`、再在同一起点插入零长补丁，排序后插入排在替换**之后** ——
> 实测后果：给没有 `w:pPr` 的段落写页码时，正文被写了两遍、`<w:pPr>` 落到 run 后面
> （`word/footer1.xml` 一看就露馅，而结构校验与自家读取器都判通过）。
> **规则**：同一位置既要改结构又要改内容时，合并成**一次**补丁；
> 分两次的前提是两个区间的起点不同（例如 `pPr` 已存在时，正文补丁从 `pPr.end` 开始）。

### 2.3 事务流程（§十一）

```
解析参数 → 校验路径/类型/大小 → 获取文件锁 → 打开工作簿
   → 检测宏/外链/签名 → 在内存中生成补丁 → 序列化
   → 写暂存文件 → 重新打开 + 重读变更单元格校验
        ├─ 校验失败 → 丢弃暂存 → 原文件不变 → 返回 OUTPUT_VALIDATION_FAILED
        └─ 校验通过 → 原子 rename 替换 → 释放锁 → 清理临时目录
```

**关键约束**：验证失败时 `commit()` 抛错且绝不 `rename`，因此原文件字节不变。
集成测试对此有断言。

### 2.4 安全模型

| 威胁 | 对策 | 位置 |
|---|---|---|
| 路径穿越 | 归一化后强制前缀匹配工作区根；拒绝 UNC/设备路径/空字节 | `resolveSafePath` |
| 伪造扩展名 | 读 magic bytes（PDF/OLE/ZIP），ZIP 再查包内标志部件 | `detectFileType` |
| 压缩炸弹 | 条目数 ≤8192、单条 ≤256MB、总量 ≤1GB、压缩比 ≤200 且解压量 >1MB 才判定 | `ZipPackage.open/read` |
| XML 实体攻击 | 直接拒绝含 DOCTYPE 的文档，不做实体展开 | `XmlDoc.parse` |
| XML 炸弹 | 字节数 ≤64MB、节点数 ≤200 万、深度 ≤256 | `XmlDoc.parse` |
| 加密文件 | 识别 OLE 容器 → `PASSWORD_REQUIRED`，不解密不猜测 | `Workbook.open` |
| 宏 / 外链 / 签名 | 检测并**警告**，从不执行宏、不更新外链、不访问网络 | `securityWarnings` |
| 并发写同一文件 | 独占锁文件 + mtime 超时回收（10 分钟） | `FileLock` |
| 误删 / 误覆盖 | 破坏性操作需 `confirm=true`；创建默认拒绝覆盖 | 工具层 |
| 资源泄漏 | 随机临时目录；成功/失败路径均清理；测试断言无残留 | `TempWorkspace` / `Transaction` |

**未做**（诚实声明）：进程级 CPU/内存配额、审计日志持久化、多租户权限。
这些属于阶段 7 范围。

## 四、工具接口草案

### 4.1 统一响应信封

```jsonc
{
  "success": true,
  "request_id": "uuid",
  "summary": "✍️ 已写入「销售数据」7 个单元格：A1、B1、A2…",  // 给模型的紧凑摘要
  "document_id": "sha256",
  "output_file": { "name": "x.xlsx", "path": "...", "size": 12345, "mime_type": "...", "sha256": "..." },
  "warnings": [{ "code": "FORMULA_NOT_RECALCULATED", "message": "..." }],
  "changes": [{ "type": "cell_update", "sheet": "数据", "range": "B2", "formula": null }],
  "performance": { "duration_ms": 42, "memory_bytes": 12345678 },
  "data": { /* 工具特有载荷 */ },
  "error": null
}
```

失败时 `success:false`，`error` 含 §13 要求的全部字段：
`code / message / details / retryable / solution / partial_output / needs_rollback / needs_confirmation`。

### 4.2 破坏性操作确认位

| 操作 | 要求 |
|---|---|
| `office_delete_worksheet` | `confirm=true` |
| `office_delete_file` | `confirm=true` |
| `office_execute_operation`（计划被判为破坏性/大范围） | `confirm=true` |
| `office_create_document` 覆盖既有文件 | `overwrite=true` |

### 4.3 预览 → 执行 → 回滚

```
office_preview_operation  →  { plan_id, impacts[], destructive, risky, requires_confirmation }
office_execute_operation  →  { plan_id, backup_id, output_file, changes[] }
office_rollback_operation →  按 backup_id 校验哈希后恢复
office_get_task_status    →  查询计划状态（previewed/executed/failed/cancelled/rolled_back）
office_cancel_task        →  取消未执行的计划
```

**语义约定**：计划一旦 `executed` 不可重复执行；`rolled_back` 后允许重做（重新应用同一变更）。

## 六、性能基准（对照 §14.4 参考目标）

测量方式：`node test/perf.test.mjs`（`--large` 追加 50MB 级场景）。
环境：Node v24.20.0 / win32 x64 / Intel i5-10300H @ 2.5GHz / 单次运行，未取多次平均。

### 小型工作簿（1000 行 × 10 列，0.1 MB）

| 场景 | 实测 | 文档目标 | 结论 |
|---|---|---|---|
| 读取（打开 + 读全表 10010 单元格） | **66 ms** | ≤ 2000 ms | ✅ 30 倍余量 |
| 修改（改 2 个单元格并保存） | **124 ms** | ≤ 3000 ms | ✅ 24 倍余量 |
| 重新打开并校验 | 75 ms | — | ✅ |

### 中型工作簿（20000 行 × 10 列，200010 单元格，1.2 MB）

| 场景 | 实测 |
|---|---|
| 仅解析 ZIP 中央目录（不解压） | **1.9 ms** |
| 读 100 行区域 | 1108 ms |
| 读全表 200010 个单元格 | 763 ms |
| 改 2 个单元格并保存 | 2067 ms |
| 重新打开并校验 | 1701 ms |
| 进程 RSS | 665 MB |

**诚实结论**：本实现是 **O(工作表规模)** 而非 O(区域规模) —— 即使只读 100 行，
也要先解析整张工作表的 XML。中型表每次操作 1–2 秒可接受；**100 MB 级文件当前不可用**
（会触及 512MB 单文件上限与内存上限），流式解析属于阶段 7。

### 本轮定位并修复的性能缺陷

| 缺陷 | 原因 | 修复 | 效果 |
|---|---|---|---|
| 写入 20 万单元格耗时 **29.1 s** | `XmlDoc.patch()` 每个补丁都全扫已有补丁做重叠检测，O(n²) | 补丁按 `start` 有序 + 二分插入，只与相邻项比较 | **→ 4.6 s（6.3×）** |

| 多次批量写入慢 | 每次 `#flush` 立即全量 rescan | 标记脏 + 按需懒 rescan | 保留正确性，去掉重复解析 |

3. **加密 PDF 必须拒绝改写**：不带口令改写只会产出损坏文件，因此返回 `PASSWORD_REQUIRED`

1. **页面级 `/Resources` 是整体覆盖，不是合并**。只写一个含水印字体的资源字典，会让页面

3. **字体字典与外层资源字典必须内联**。写成 `/Resources → 对象 → /Font → 对象 → /Wm → 对象`

   这些文字**。定位方式：造一个「同一页两个内容流」的最小样本，Word 能读到第二个流；

**这一轮踩到的三个坑（都是「结构合法但语义错了」的类型）**：

1. **书签的 `/Dest` 会把被丢弃的页面拉回来**。拆分时只从 `/Kids` 摘引用是不够的：
   `/Outlines`、命名目标、链接批注、结构树的 `/Pg` 都可能直接指向页面对象，可达性遍历
   于是把整页内容又写回新文件 —— 实测「拆 1 页出来，字节里仍有 3 个页面对象」。
   修法是按容器删除这类引用（数组项／`/Dest [页 …]` 整项／字典键），并报告清理条数。
   **顺带纠正了一个错误的验证手段**：原先用「搜不到被删页的正文文字」当作泄漏检查 ——
   内容流是压缩的，正文本来就不以明文出现，这条检查**永远会通过**。
   真正的硬不变量是「字节里 `/Type /Page` 出现次数恰好等于页数」。
2. **trailer 的间接引用漏了生成号**。新 trailer 一开始写成 `/Root 1 R`、`/Info 2 R`；
   规范里引用必须是 `num gen R` 三段式，`/Root 1 R` 会被解析成「数字 1 加一个 R 记号」，
   于是目录与元数据**静默丢失**（我们的读取器靠扫描 `/Type /Catalog` 兜底，所以没立刻暴露）。
3. **trailer 查找没有以 `startxref` 为准**。原先按「有没有 trailer 关键字」猜，遇到
   「经典 trailer + 交叉引用流并存」的文件会取错那一段，`/Info` 也跟着丢。
   现在严格按 `startxref` 指向的内容决定：指向 `xref` 就取偏移最大的经典 trailer，
   指向 `N G obj` 就取那个交叉引用流对象的字典（`/Info` 可能是**内联**的，两种形态都要处理）。

另外补了一个交互 bug：`rewrite()` 原先只读对象表，而 `updateMetadata` 这类操作把新字典放进
「待写回」队列，于是「先改元数据再重写」会静默丢掉修改；现在待写回的值优先。

**2026-09-23 运维教训：不要在 DSH 运行期间于 profile 里跑 `pnpm install`**

`pnpm install` 会按 `package.json` 收敛**整棵** node_modules —— 它不只处理本插件，还会去替换别的插件，
其中包括被运行中服务占用的原生包（实测 `failed to remove existing directory … 拒绝访问 (os error 5)`，
退出码 1）。后果是 profile 里其它插件也被牵连改写，随后**整个插件树罢工**。
现在同步安装副本改用 `npm run sync:profile`（纯文件复制，只碰 `node_modules/dsh-exp-office/` 一个目录），
`pnpm install` 只在 DSH 停止时执行。这条与「插件契约」一样，属于**开发流程本身的约束**。

**2026-09-23 事故：插件树加载失败，`dsh web` 起不来**

- **现象**：`dsh web` 报 `failed to apply loader entry dsh-exp-office ... TypeError: Invalid effect`
  （`@deepseek-ai/cordis/lib/index.js` 的 `safeCollect` 抛出），整个插件树加载失败。
- **根因**：`apply` 末尾 `return { registered, define_tool_source, manifest }`。Cordis 的 effect 契约是
  「清理函数 / `null` / `undefined`，或产出它们的 Promise/迭代器」；Promise resolve 成普通对象后
  进入 `safeCollect`，既不是函数也不是空值 → `TypeError: Invalid effect`。
- **为什么测试全绿没拦住**：测试里 `await apply(ctx, ...)` 拿到返回值却从不检查它，只断言工具注册数。
  于是「插件在真实加载器下能不能装载」这一环从来没被覆盖 —— 与前面几次事故同一类病根：
  **测试绕过了真实契约**。
- **修复**：`apply` 不再 return 摘要（摘要改写 `ctx.logger.info`）。源码与 profile 里的安装副本同步修改
  （`file:` 依赖是复制而非软链，两处都要改）。
- **补上的四道闸门**：
  1. `apply` 返回值契约断言：必须 resolve 为 `undefined`/`null`/函数；
  2. **用真实 Cordis 的 `Context` + `provide('tools')` 装载并 await**（与 DSH 装载路径一致）；
  3. **反例测试**：apply resolve 成普通对象时真实加载器必须抛 `Invalid effect` ——
     保证第 2 条不是碰巧通过；
  4. `npm run verify:boot`（`test/profile-boot-check.mjs`）：检查「profile 安装副本 vs 工作区」的
     **逐字节漂移**（副本不同步是这类问题的另一半来源），再从 profile 按包名解析、用真实 Cordis 装载，
     并断言工具数与 `dsh.plugin.json` 一致。
- **注意**：`dsh --profile web --dump-config` 只组合配置树、**不 apply 插件**，这次事故它照样通过 ——
  不能用它当启动检查。

**下一步建议顺序（以及需要你拍板的两件事）**：

1. **PDF 拆分/合并**。合并需要跨文件搬运对象图（字体、资源、xref 全部重编号）；
   若只做「拆分导出」，用页面树摘除最省事，但**未选页面的内容仍留在文件字节里**，
   对外分发会泄密——所以我倾向于先做**对象图重写**（顺带回收字节、消除增量更新的体积增长），
   再做拆分/合并。
2. **原地文本改写（叠加式之外的下一步）**。需要解析并重建内容流与字体子集，
   难度与出错面都明显高于叠加式；建议先补齐**渲染级回归**手段（见第 3 条）再动。
3. **渲染级视觉回归**。本机没有可自动化驱动的 PDF 渲染器，这是「旋转/斜向水印的视觉」无法验证的
   根因。可选路径：给测试环境装一个 PDF→PNG 的渲染器（pdfium/pdfjs + canvas），
   或利用 WPS PDF 的 COM 接口（本次尝试时它会弹 UI 卡住，未成功驱动）。
4. **风险 #4（行列移位与公式引用）**：只警告，还是实现引用重写。
5. **阶段 7 流式处理**：支撑 100 MB 级文件（当前全量载入 + 512 MB 上限保护）。

**PDF 解析的关键取舍**：不做交叉引用表遍历，改为**全文件对象扫描 + 对象流展开**。
理由是现代 PDF 普遍使用交叉引用流与对象流，完整实现两者代码量与出错面都很大；
按对象扫描对「读取」更宽容（尾部截断或增量更新链断裂时仍能读出内容），
代价是失去交叉引用一致性校验能力 —— 因此 `validate()` 把「交叉引用表一致性」
如实列进 `not_checked`，而不是假装校验过了。

**PPTX 适配器中发现的两个 OOXML 陷阱（值得记录）**：

1. **命名空间属性撞名**：`<p:sldId id="256" r:id="rId2"/>` 同时带无前缀的 `id` 与
   `r:id`。按本地名匹配取 `id` 会拿到幻灯片编号 `256` 而不是关系 ID，
   结果是「演示文稿有 4 页，读出来 0 页」，而所有检查项都显示正常。
   必须按完整属性名精确取 `r:id`。
2. **同一个语义有两个存放位置**：隐藏幻灯片既可能写在 `presentation.xml` 的
   `<p:sldId show="0">`，也可能写在**幻灯片部件根元素**的 `show="0"` 上。
   PowerPoint 用的是后者。只按前者实现会得到「没有隐藏页」的自信错误结论 ——
   最终靠「转 PDF 只导出 3 页」这个独立信号才确认读法是对的。

**本窗口修掉的一个真 bug（值得记录）**：DOCX 适配器最初把「树过期」与「包待写回」
合成同一个脏标记，结果「写 → 读 → 写」序列里一次读取就清掉了脏标记，`save()` 跳过写回、
**修改静默丢失**。直接 `save()` 的单元测试全绿，是「先读一次再 save」的集成测试暴露的。
修复方式与 XLSX 一致：拆成 `#treeStale`（读取前重建树）与 `#needsFlush`（save 时写回包）两个独立标记。

**另一个更值得记录的 bug：字节级测试说「通过」，Word 说「功能没了」**

`update_paragraph` 会整段替换 run 内容。当目标段含批注锚点（`commentReference` /
`commentRangeStart/End`）、书签定界（`bookmarkStart/End`）或修订标记（`w:ins`）时，
这些锚点会随 run 一起被删掉 —— **`comments.xml` 部件本身逐字节未变**，
所以「无关部件未被改动」的断言判定 ✅；但锚点没了、引用断了，
用 Word 打开时批注从 1 条变成 0 条、书签从 1 个变成 0 个、修订从 2 处变成 1 处。

这暴露了保真度测试的一个盲区：**「部件没变」不等于「功能还在」**。

修复方式是加保护性检查：`updateParagraph` / `deleteParagraph` 先扫描目标段落里的
14 类结构化标记（书签、批注锚点、修订、域代码、超链接、内容控件、脚注尾注引用），
命中就默认**拒绝执行**并列出具体标记，需显式传 `allowMarkupLoss`（工具参数 `allow_markup_loss`）
才继续；同时新增 `paragraphSafety(index)` 供调用方在动手前查询哪些段落可安全改写。

修复后 Word 复核：编辑后的文档与原始样本特性数量**完全一致**。

教训：**字节比对 + 真实软件复核，两者都要** —— 前者能证明「没乱改」，后者才能证明「功能还在」。
只做前者会得到一个自信的、错误的「通过」。

**第三个 bug：一个永远为假的布尔值**

`detectFileType` 会把「按字节识别出的类型」与「扩展名声明的类型」比对，不一致就报
`extension_mismatch`，工具提示里也会警告「扩展名与实际类型不符」。
但 `finalize()` 的调用方传进去的是**已识别类型**的规格，于是两个值永远相等 ——
`mismatch` 恒为 `false`。

后果：把一个 `.docx` 改名成 `.xlsx` 交给插件，它会正确识别出这是 docx，
但**不会提示扩展名不符**；宏文件改名同理。而 PDF 改名那条路径是对的
（它传的是声明扩展名的规格），所以既有测试一直绿着 ——
「伪造扩展名会被识破」这个测试用的是 PDF 样本，恰好绕过了这条错误路径。

发现方式：既然 README 声称「宏按原字节保留」，就该拿宏样本去验；造宏样本时顺手加了
「改名也要识破」的断言，一跑就暴露了。**为一个未验证的声明去补测试，往往能顺带挖出旁边的 bug。**

修复：`finalize()` 只接收扩展名，自己查声明规格。新增两条回归测试
（docx→xlsx、xlsm→xlsx 改名）。

**第四条：宏验证的边界（不是 bug，是诚实）**

用 Excel COM 写 VBA 需要开启「信任对 VBA 工程对象模型的访问」，默认关闭；
系统里也没有现成宏文件可复用。开启该设置属于**改动用户的 Office 安全配置**，未获授权不做。
因此宏测试用**合成** `vbaProject.bin`：证明了检测与字节保留，**未证明** Excel 能运行宏。
这条边界写进了 README 与测试输出，不含糊过去。

**第五条：读与写各写一套遍历，迟早错位**

PPTX 写入需要「按形状下标定位」。最初 `readSlide` 与写入方法各写了一套 spTree 遍历，
而且各自做了一次类型细化（把 `graphicFrame` 细分成 table / chart）——
结果读出来的类型是 `table`，写入时拿到的却是 `graphicFrame`，
同一份形状列表在两处语义不同。更险的是：**只要下标顺序碰巧一致，这种 bug 就不会暴露**。

修复：把遍历**和**类型细化合并到唯一的 `#shapeNodes()`，读写都从它取。
顺带修掉一个相关问题：`find(txBody)` 会递归找到表格单元格里的 `<a:txBody>`，
把表格误判成「可写文本的形状」——现在只接受 `<p:sp>` 的**直接子** `txBody`。

教训：**同一条信息在两处分别计算，就是两处会不一致的地方。**
只要读和写需要共享一个「下标 → 对象」的映射，这个映射就必须只有一个来源。

**第七条：三个适配器各有一份同样的容器操作**

写完 PPTX 后回看，`xlsx.js` / `docx.js` / `pptx.js` 各自实现了一份
「加内容类型声明 / 加关系 / 删关系」。逻辑相同、细节微异（一个按对象传参、
一个按位置传参、一个不检查重复）。这和第五条是同一个病：
**同一件事有两种实现，迟早分叉**，而且分叉时会表现成「某个格式偶尔写坏关系」。

修复：把五个 OPC 容器操作下沉到 `ooxml.js`，三个适配器共用：
`ensureContentTypeDefault` / `ensureContentTypeOverride` / `removeContentTypeOverride` /
`addRelationshipTo` / `removeRelationshipFrom`。

顺带修掉一处隐患：`addWorksheet` 原本用 `nextRelId()` 自己算关系 ID，
同时又调用追加函数再算一次。两处算法一致时看不出问题，一旦分叉，
`workbook.xml` 里的 `r:id` 就会指向另一条关系。现在只用追加函数的返回值。

迁移后三个适配器共减少约 120 行重复实现，320 项断言与三个真实软件（Excel / Word / PowerPoint）复验全部通过。

同一轮里还把**图片工具**（`detectImageType` / `readImageSize` / `imageContentType` /
`resolveImageExtent` / `EMU_PER_PX`）也下沉到 `ooxml.js` —— PPTX 插图必然需要
DOCX 已有的那套「按魔数判类型、只读文件头取尺寸、按 96 DPI 换算 EMU」逻辑。
`docx.js` 保留同名再导出，因此工具层与既有测试无需改动。

**第八条：把可变状态放在模块级**

PDF 文本提取器最初用模块级的 `pendingFont` / `pendingStrings` 记录解析中间状态。
这在单次调用里看不出问题，但**并发调用会互相污染**，跨页调用也会带着上一页的残余。
改成函数局部变量。

同一模块里还有一处「条件写反」：`/F1 10.5 Tf` 中 `/F1` 是字体名、`Tf` 才是操作符，
我最初写成「名称操作数等于 `Tf` 时才记录字体」——于是字体名永远记录不上，
**中文全部提取成乱码**。结构化解析里这类「把值当成了操作符」的错误很典型，
而且它不会崩、不报错，只是安静地输出垃圾。

**第六条：少一层 `../` 的静默失败**

新增幻灯片时要写一条指向版式的关系，目标是相对 `ppt/slides/` 的路径。
最初写成了 `slideLayouts/slideLayout12.xml`（忘了 `../`），正确应是
`../slideLayouts/slideLayout12.xml`。

危险之处在于：**文件照样能打开**，PowerPoint 也不报错 —— 只是新页拿不到版式，
标题与正文的样式静默回退。这类「不报错的错误」只能靠「读回新页的 version 路径
是否与参照页一致」这种语义断言抓住，而不是靠「能不能打开」。
